Fail-safe OTA Updates on Raspberry Pi 4

Using Thistle (A/B Root Filesystem)

Start the Guide

Overview: What You’re Doing

You are preparing a Raspberry Pi 4 to support fail‑safe over‑the‑air (OTA) updates of its root filesystem using an A/B partition scheme (two root partitions). At any time, the Pi boots from either partition A or B. Updates are written to the inactive partition. If the update works, the Pi switches to the new partition; if it fails, it automatically falls back to the previous partition. You’ll use Thistle tools tuc (on the Pi) and trh (on your PC) to manage and apply updates.

Step‑by‑Step Guide (Collapsible)

1) Prepare USB and SD card with Raspberry Pi OS (on your PC)

Use Raspberry Pi Imager to flash Raspberry Pi OS Lite to both drives:

  • USB drive → becomes the “utility OS” (suggested hostname: rpi4-util)
  • Micro SD card → becomes the “demo OS” (suggested hostname: ota-demo)

During “OS customization”, set:

OptionReason
HostnameTo identify the device on the network.
Username + PasswordFor SSH login.
Wi‑Fi credentials + enable SSHAllow headless access (no monitor/keyboard needed).

After flashing:

  • Insert the USB drive into the Pi.
  • Do not insert the SD card yet.
2) Boot Pi (USB only) into Utility OS and SSH in

Why: We want to edit/partition the SD card without booting from it (which would lock it). So we boot from USB, then insert the SD and modify it.

ssh <username>@<rpi4-ip-addr>

→ Connect to the Pi over the network (find its IP on your router or via a network scan).

3) Update the Utility OS and enable serial console 
sudo apt update

→ Refresh the list of available packages.

sudo apt dist-upgrade -y

→ Install all updates (including kernel and dependencies).

sudo rpi-eeprom-update -a

→ Update Raspberry Pi bootloader firmware. Older Pi 4 bootloaders may break A/B boot.

sudo raspi-config

→ Enable Serial Port in Interface Options so the UART pins (GPIO 14/15) can output boot logs.

4) Insert SD card and inspect partitions 
lsblk /dev/mmcblk0

→ List block devices; confirm the SD has: p1 boot (FAT32), p2 rootfs (ext4). p3 does not exist yet.

5) Create the “B” root partition 
sudo fdisk /dev/mmcblk0

→ Launch partition editor to create the new rootfs B partition.

# Inside fdisk:
p          # print current partitions (note end of p2, e.g., 5390335)
n          # new primary partition
# First sector → NEXT FREE SECTOR (e.g., 5390336)
# Last sector  → press ENTER to use the rest of the card(e.g. 123596799)
w          # write changes

→ Create mmcblk0p3 using the free space after p2 and save.

PartitionPurpose
mmcblk0p1/boot
mmcblk0p2Rootfs A
mmcblk0p3Rootfs B
6) Mount the rootfs and edit files 
mkdir mymount
sudo mount /dev/mmcblk0p2 mymount/

→ Mount partition p2 (default rootfs) to a temporary directory so we can edit its files.

Modify /etc/fstab:

sudo nano mymount/etc/fstab
# Change any '/boot/firmware' entry to:
/boot    vfat   defaults    0  1

→ Raspberry Pi OS expects the boot partition at /boot, not /boot/firmware. If not fixed, the system may fail to mount /boot after OTA.

7) Add the Thistle Update Client (tuc) 
wget https://downloads.thistle.tech/.../tuc-1.5.0-aarch64-unknown-linux-musl.gz

→ Download the tuc binary.

gunzip tuc-1.5.0-aarch64-unknown-linux-musl.gz

→ Decompress the binary.

chmod +x tuc-1.5.0-aarch64-unknown-linux-musl

→ Make it executable.

sudo cp tuc-1.5.0-aarch64-unknown-linux-musl mymount/usr/bin/tuc

→ Place it at /usr/bin/tuc inside the mounted rootfs so it’s available on the Pi.

sync
sudo umount mymount

→ sync flushes data to disk; umount safely detaches the partition.

8) Enable UART on the demo OS (boot partition) 
sudo mount /dev/mmcblk0p1 mymount/
sudo nano mymount/config.txt
# Add this line:
enable_uart=1
sync
sudo umount mymount
sudo poweroff

→ Ensure the demo OS outputs boot logs over UART after the switch. Power off to safely remove power before moving to the SD‑boot phase.

9) Reboot Pi with the SD card (demo OS boots)

Unplug the USB drive (utility OS) and keep the SD card inserted.

minicom -b 115200 -D /dev/ttyUSB0

→ Open a serial console on your PC to watch the boot logs.

10) Confirm system status 
uname -a

→ Show OS/kernel version; confirm you’re now booted into ota-demo.

mount | grep /dev/mmc

→ Verify that /dev/mmcblk0p2 is currently mounted as /.

11) Build the OTA update package (on your PC) 
curl -O https://downloads.thistle.tech/.../four-v1.5.0-updated.rootfs

→ Download the alternative rootfs image (your updated OS).

export THISTLE_TOKEN=$(cat)

→ Temporarily set your Thistle access token in the environment. (On PowerShell use $env:THISTLE_TOKEN.)

./trh --signing-method="remote" init -persist="/boot"

→ Initialize Release Helper and store metadata under /boot for the client to read/update.

./trh --signing-method="remote" prepare --target=./four-v1.5.0-updated.rootfs

→ Create a manifest and sign the rootfs image.

./trh --signing-method="remote" release

→ Upload the bundle to the Thistle backend, making it available for devices.

12) Create config.json and copy it to the Pi

If your setup uses a persistent directory, set it to /boot/persist so it survives A/B switching.

{
  "bootloader": "RaspberryPi",
  "part_a": "/dev/mmcblk0p2",
  "part_b": "/dev/mmcblk0p3"
}

→ Tell the update client which bootloader is used and which partitions are A and B.

# Copy to Raspberry Pi (adjust IP and user)
scp config.json thistle@192.168.1.102:~/tuc-config.json
# On the Pi:
sudo cp ~/tuc-config.json /boot

→ Keep config.json in /boot so it persists across partition switches.

13) Run the update 
sudo tuc -c /boot/tuc-config.json

→ Contact the Thistle backend, download the bundle, install to the inactive partition (p3), set boot order, and reboot.

After reboot:

mount | grep /dev/mmc

→ Should show /dev/mmcblk0p3 mounted as / (the new rootfs).

cat message_from_thistle.txt

→ If it prints the test message, the OTA update worked.

# Finalize (mark update good)
sudo tuc -c /boot/tuc-config.json

→ Confirm the update is good so future boots continue from the updated partition.

After the OTA update… what happens to partition 2?

Before the update, you boot from /dev/mmcblk0p2 and mmcblk0p3 is empty/inactive.

sudo tuc -c /boot/tuc-config.json

→ Thistle downloads the new rootfs image and writes it into the inactive partition (e.g., mmcblk0p3).

During the first reboot after the update, the bootloader switches the active partition to mmcblk0p3. Partition 2 still exists; it becomes the backup/fallback.

PartitionRole after update
/dev/mmcblk0p2Standby / fallback (old system)
/dev/mmcblk0p3Active rootfs with updated system

What does “update status 0 → 2” mean?

These are internal Thistle status codes that describe the status of the OTA cycle.

CodeMeaning
0Idle — no update was attempted yet
1Update in progress
2Update successfully downloaded and applied
3Update failed and fallback triggered

So, update status 0 → 2 means it changed from Idle (0) to Success (2) — update applied and Pi now boots from the updated partition.
